# 04 · 上架准备清单

> 把「脑力大冒险」从"能装的 APK"变成"应用商店里的一个 App"，需要补的不是功能，而是**材料与合规**。
> 本篇把现状盘清楚，把待办列成可勾选的清单。原有的国创赛申报材料（`申报材料/`）里有不少东西能直接复用。

## 一、先做三个决策

| 决策 | 现状 | 建议 |
|---|---|---|
| **应用名** | 仓库/App/Release 都是 **脑力大冒险**；申报材料对外是 **学海星槎** | 二选一后全局统一。**只改显示名**（`strings.xml` 的 `app_name`、商店文案、README），**不要改包名** |
| **包名** | `com.brainquest.game` | **保持不变**。改包名 = 全新应用：线上老用户无法原地更新、自有更新链（按 versionCode 匹配补丁）全部失效、服务器昵称积分数据与新包不再对应 |
| **版本策略** | `versionCode` 单调递增（当前 31） | 继续单调递增，别回退；商店对已上架的 versionCode 只接受递增 |

## 二、隐私合规（审核最容易卡的一关）

### 现状盘点：这个 App 到底收集/上传了什么

| 数据 | 是否离开设备 | 去向 | 依据代码 |
|---|---|---|---|
| 游戏进度、金币、等级、错题本、设置 | ❌ 默认只在本地 | DataStore（`PlayerState`） | `data/SaveStore.kt` |
| **整份存档 JSON**（含昵称、进度、错题本、云存档码） | ✅ **仅当用户主动点「上传存档」** | 公网服务器 `/opt/pk/saves/<码>.json`，**明文 JSON** | `AppViewModel.exportSaveJson` → `PkClient.sendCloudPut` |
| 昵称、客户端版本、对局答案与得分 | ✅ 联机对战时 | 公网服务器（ELO 积分按昵称分科目持久化） | `game/pk/PkBattleScreen.kt`、`update-server/pk_server.py` |
| 第三方 SDK / 广告 / 埋点 / 崩溃上报 | ❌ **一个都没有** | — | 依赖清单只有 AndroidX / OkHttp / Java-WebSocket / kotlinx.serialization |

> 结论：数据面很干净，**没有广告与分析 SDK**，这是审核与隐私政策的有利条件。
> 但"云存档明文上传公网服务器"这一点必须在隐私政策里如实写明，并且**建议先把
> `03-待办与路线图.md` P1 的「云存档身份校验」做完再上架**（明文存储 + 无鉴权，既是审核问询点也是真实风险）。

### 隐私政策必须写清的 4 项
1. **收集范围**：本地存档（不同步）+ 用户主动上传的云存档 + 联机对战的昵称与成绩。
2. **用途**：仅用于跨设备恢复进度、联机匹配与排行榜，**不用于广告、不共享给第三方**。
3. **存储与安全**：存在自有公网服务器（可写地域/IP 所属），保存期限、以及用户如何删除。
4. **联系方式与未成年人**：本项目面向学生（含未成年人），要写监护人同意口径与联系邮箱。

### 权限说明（如实描述用途，商店表单会问）

| 权限 | 用途 |
|---|---|
| `INTERNET` | 联机对战、云存档、检查更新 |
| `VIBRATE` | 答对答错/撞击的震动反馈（可在设置里关） |
| `POST_NOTIFICATIONS` | 应用内更新完成后发一条"更新完成"通知（Android 13+ 需运行时授权） |
| `REQUEST_INSTALL_PACKAGES` | **自有增量更新需要拉起系统安装器**。这是审核重点：商店版本建议评估是否保留（若改用商店更新通道，可去掉此权限，自有更新降级为"可选"） |

### 需要整改的点（上架前）
- [ ] `android:usesCleartextTraffic="true"` 收紧：改为**按域名白名单**（`network_security_config.xml`），只放行联机与更新所需的 `ws://8.148.192.129:8765` 与更新地址；更好的是服务器上 TLS，走 `wss://` / `https://` 后彻底关掉明文
- [ ] 隐私政策必须能**在 App 内访问**（设置页加入口）且应用商店表单填写链接
- [ ] 提供**数据删除通道**（例如设置页"删除云端存档"按钮，或隐私政策里的邮件申请方式）
- [ ] 云存档改为加密存储（见 P1 待办），顺带解决"服务器明文存有用户进度"的表述

## 四、技术收紧项

- [ ] **targetSdk 政策**：当前 `targetSdk = 34`。各商店对 targetSdk 有最低要求且逐年提高，上架前按当时政策核对是否需要升到更新的 API（升 targetSdk 后要回归：通知、安装器、后台启动限制这几处已知敏感点）
- [x] **64 位支持**：APK 已包含 `arm64-v8a / armeabi-v7a / x86 / x86_64` 四套原生库，无 64 位合规问题
- [x] **混淆与资源压缩**：debug/release 都已开 R8（`proguard-rules.pro` 已保留 serialization / WebSocket / 题目模型，改动时别删）
- [x] **minSdk 26**：覆盖 Android 8.0+，符合主流商店下限
- [ ] `REQUEST_INSTALL_PACKAGES` 与自有更新体系的关系要按渠道区分（见下节）

## 五、签名与"双通道更新"策略（上架后最容易出问题的地方）

现状是**自有更新体系**：App 内「设置与更新」检查 GitHub Releases 的 manifest，按 versionCode 下增量补丁、
合成后拉系统安装器安装。上架后会多出**商店更新通道**，两条通道必须约定清楚，否则会互相覆盖或反复提示：

| 渠道 | 建议做法 |
|---|---|
| 上架版（商店包） | 关闭/隐藏应用内"检查更新"的安装动作，只保留"内容热更新"（题库包与 APK 无关，任何渠道都能用）。安装包更新交给商店 |
| 自发行版（GitHub） | 保持现状：增量补丁 + 全量兜底 |
| 两者共同点 | **签名必须一致**（同一个 keystore）。若商店包与 GitHub 包签名不同，用户从一条通道换到另一条必须卸载重装 |
| versionCode | 两条通道共用同一份 `versionCode` 递增序列，避免商店因 versionCode 回退拒绝更新 |

- [ ] 上架前把「检查更新」做成**可配置开关**（例如按 BuildConfig 或渠道字段判断），商店包默认只更新内容包
- [ ] keystore 做异地备份（见 `03-待办与路线图.md` P0），上架后密钥丢失等于产品生命周期终结
